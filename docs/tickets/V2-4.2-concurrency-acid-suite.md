## Goal
Build an automated concurrency test harness that executes continuous analytical queries against Cube while a simulated data reload pipeline unloads, stages, and commits a major table update, verifying that zero queries experience torn reads, partial partitions, or lock contention.

## Acceptance Criteria
1. Background workers execute continuous high-frequency aggregation queries against `AnnuityQuotation` during a live table reload.
2. Asserts that every query returns data strictly from either the pre-reload snapshot (v_old) or post-reload snapshot (v_new) without intermediate states.
3. Proves zero lock timeouts or table unavailable exceptions during the commit window.
4. Generates concurrency verification telemetry proving 100% snapshot isolation under load.

## User Stories
1. *As an operations engineer*, I want tangible verification that monthly data batch reloads do not degrade or corrupt customer queries, so that we can run data reloads during business hours.
2. *As an enterprise architect*, I want empirical evidence of DuckLake's snapshot isolation, proving that the migration from raw Parquet globbing successfully resolved torn reads.

## Seam
Multi-threaded Python concurrency test harness running queries in parallel with an active table reload.
