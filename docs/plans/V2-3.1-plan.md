## 1. Architectural Scope & Contract

- **Goal**: Author production deployment manifests for the Dual Delivery Architecture ([`ADR-0004`](../adr/0004-dual-delivery-topologies.md)), producing a single unified container image (`scbi-cube:2.0`) deployed to Google Cloud Run (`scbi-cube`) for the REST API (port 4000) and to a dedicated internal Compute Engine VM (`scbi-cube-sql`) via `systemd` for the SQL API (port 5432).
- **Single Artifact Principle**: Both Cloud Run and GCE VM run the identical image (`scbi-cube:2.0`) with runtime mode controlled strictly via environment variables (`CUBEJS_REST_API`, `CUBEJS_PG_SQL_PORT`).

## 2. Step-by-Step Implementation Tasks

1. **Author `version-two/infra/Dockerfile`**:
   - Multi-stage build using `node:22-bookworm-slim` (`builder` stage installing production dependencies for `version-two/cube/package.json`, and `runtime` stage packaging Node 22, Cube 1.7.x, `@duckdb/node-api`, `version-two/cube/`, `version-two/ducklake/`, and non-root user execution).
   - Expose ports `4000` (REST API) and `5432` (SQL API via `CUBEJS_PG_SQL_PORT`).

2. **Author `version-two/infra/cloudrun-rest.yaml`**:
   - Knative `Service` manifest (`apiVersion: serving.knative.dev/v1`, metadata name `scbi-cube`).
   - Configured with Serverless VPC Access Connector (`run.googleapis.com/vpc-access-connector`, `run.googleapis.com/vpc-access-egress: private-ranges-only`), autoscaling (`minScale: "1"`, `maxScale: "10"`), 2 vCPU / 4Gi memory, port `4000`, and Google Secret Manager `valueFrom.secretKeyRef` bindings for `CUBEJS_API_SECRET` and `DUCKLAKE_DB_URL`.

3. **Author `version-two/infra/gce-sql-systemd.service`**:
   - Systemd unit file (`[Unit]`, `[Service]`, `[Install]`) for `scbi-cube-sql.service` on Debian 12 GCE VM (`e2-standard-4`).
   - Runs `scbi-cube:2.0` bound strictly to internal VPC interface on port `5432` (`CUBEJS_PG_SQL_PORT=5432`), loading secrets from `/etc/scbi-cube/sql.env`, with automatic restart and health verification.

4. **Enhance `version-two/cube/cube.js` Dual-Mode Runtime (`startCubeSqlServer`)**:
   - Add `startCubeSqlServer(options)` in `version-two/cube/cube.js` listening on TCP port `5432` (or `CUBEJS_PG_SQL_PORT`) so the same artifact serves both REST (`4000`) and SQL API (`5432`) and validates `CUBEJS_PG_SQL_PORT` coherence.

5. **Author `version-two/tests/test_v2_3_1_dual_delivery_infra.py`**:
   - **AC1 (`test_multistage_dockerfile_node22_cube17_duckdb`)**: Verifies multi-stage `Dockerfile` (`FROM node:22... AS builder`, `FROM node:22... AS runtime`), Cube 1.7.x packaging, and `EXPOSE 4000 5432`.
   - **AC2 (`test_cloudrun_rest_yaml_vpc_and_secret_manager`)**: Verifies `cloudrun-rest.yaml` configures `scbi-cube`, VPC Access Connector, `containerPort: 4000`, and Secret Manager `secretKeyRef` for `CUBEJS_API_SECRET` and `DUCKLAKE_DB_URL` with zero hardcoded secrets.
   - **AC3 (`test_gce_sql_systemd_service_manifest`)**: Verifies `gce-sql-systemd.service` configures `scbi-cube-sql`, `CUBEJS_PG_SQL_PORT=5432`, `scbi-cube:2.0`, and restart policy.
   - **AC4 (`test_dual_delivery_modes_start_cleanly_on_4000_and_5432`)**: Starts the unified Cube runtime in REST mode (port 4000) and SQL mode (port 5432) and verifies both listeners respond cleanly and return identical catalog health and metric results.
