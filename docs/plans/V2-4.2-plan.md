## 1. Architectural Scope & Contract

- **Goal**: Build an automated multi-threaded concurrency test harness (`version-two/tests/test_concurrency_acid.py`) that executes continuous high-frequency analytical queries against Cube (`AnnuityQuotation`) while a simulated data reload pipeline unloads, stages, and commits a major table update (`v1` -> `v2`), verifying that zero queries experience torn reads, partial partitions, or lock contention.
- **Input Dependencies**:
  - `version-two/ducklake/init_catalog.py` (`CatalogConnection`, `initialize_catalog`)
  - `version-two/ducklake/reload_pipeline.py` (`StageTablePayload`, `build_staging_uri`, `commit_reload_batch`)
  - `version-two/cube/cube.js` (`startCubeHttpServer`, `startCubeSqlServer`, `EmbeddedDuckLakeDriver`)
  - `version-two/portal/auth.py` (`VerifiedIdentity`, `mint_cube_jwt`)

## 2. Step-by-Step Implementation Tasks

1. **Harden Snapshot Isolation & Concurrent Reader/Writer Config in `init_catalog.py` & `cube.js`**:
   - In `CatalogConnection.connect()` (`version-two/ducklake/init_catalog.py`), enable `PRAGMA journal_mode = WAL;`, `PRAGMA synchronous = NORMAL;`, and `PRAGMA busy_timeout = 30000;` (and `timeout=30.0` on `sqlite3.connect`) so concurrent readers never block or error during a catalog snapshot commit transaction.
   - In `ensureSqliteCatalogSeeded` and `EmbeddedDuckLakeDriver.query` (`version-two/cube/cube.js`), configure `PRAGMA busy_timeout = 30000; PRAGMA journal_mode = WAL;` and include `snapshotVersion` in `/cubejs-api/v1/load` and SQL API responses.

2. **Author `version-two/tests/test_concurrency_acid.py`**:
   - Spawn a multi-threaded pool of background reader workers (`ThreadPoolExecutor`, 8 concurrent reader threads) executing continuous high-frequency aggregation queries (`AnnuityQuotation.quotationCount`, `AnnuityQuotation.acceptedQuotations`, `AnnuityQuotation.quotedPurchasePrice`, `AnnuityQuotation.averageCommissionRate`) against the live Cube server.
   - Concurrently run a multi-stage table reload simulation on `scbi_cdp_mart.cnf__fact_annuity_quotations`:
     - Stage 1: Simulate multi-part Parquet unload & staging while `v1` (`129,954` rows) is serving live queries.
     - Stage 2: Execute atomic catalog commit (`commit_reload_batch`) transitioning `AnnuityQuotation` from `v1` (`129,954` rows) to `v2` (`210,500` rows), followed by a second atomic reload `v2` -> `v3` (`245,000` rows) under continuous read load, plus an aborted/invalid stage (`ReloadValidationError`) to prove failed reloads never pollute readers.
   - Verify all 4 Acceptance Criteria:
     - **AC 1**: Background workers execute continuous high-frequency aggregation queries (150+ queries) against `AnnuityQuotation` during live table reloads.
     - **AC 2**: Every single query response matches strictly one of the valid committed snapshots (`v_old` or `v_new`) across all measures simultaneously, with zero intermediate, partial, or torn states (`torn_reads == 0`).
     - **AC 3**: Zero lock timeouts, `SQLITE_BUSY` errors, HTTP 5xx, or table unavailable exceptions (`failed_queries == 0`, `lock_timeouts == 0`).
     - **AC 4**: Generates structured concurrency verification telemetry in `version-two/tests/reports/concurrency_acid_telemetry.json` proving 100% snapshot isolation under load.

## 3. Validation & Rollback Plan

- **Validation Commands**:

  python3 -m unittest discover -s version-two/tests -p "test_*.py" -v

- **Rollback**: Revert `version-two/tests/test_concurrency_acid.py`, `version-two/tests/reports/concurrency_acid_telemetry.json`, and WAL pragma additions.
- **Out of Scope**: Cross-domain 56-query REST/SQL parity matrix (covered in `V2-4.1`).
